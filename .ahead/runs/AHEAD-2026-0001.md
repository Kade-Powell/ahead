# Add durable-reference guidance and reference-updates artifact enforcement

## Define

Cola-v2 needed a place to move its documentation. AHEAD only prescribed run
artifacts and left durable references to each project. That gap forced every
AHEAD-using project to reinvent decision-record, design-doc, and runbook
conventions.

Success signals:

- AHEAD names the three durable-reference classes it standardizes and explicitly
  disclaims the categories it leaves to projects.
- Runs that alter durable behavior enumerate their reference updates as an
  artifact, closing the doc-drift gap.
- AI review sees the entire live run, not only the changeset snapshot.

## Research

Verified with `source_check` / `fetch_content` bindings to exact passages:

- **Diátaxis** — four modes distinguished by user need; anti-pattern language
  about mixing modes (diataxis.fr/start-here/).
- **MADR** — Markdown Any Decision Records template; fields Context and
  Problem Statement, Decision Drivers, Considered Options, Decision Outcome,
  Consequences; filename pattern `NNNN-title-with-dashes.md`
  (adr.github.io/madr/).
- **arc42** — twelve-section open-source architecture-documentation template;
  free even for commercial use (arc42.org).
- **Google SRE Book** — playbooks (industry: runbooks) as per-alert
  procedural documents that reduce MTTR (sre.google/workbook/on-call/).
- **Google developer documentation style guide** — layered reference hierarchy
  covering developer prose (developers.google.com/style).

DORA / Accelerate documentation-quality claim considered but not bound to an
exact passage in the available time; deliberately left out of the artifact.

## Questions

Disposed:

- Do we adopt Diátaxis or invent AHEAD taxonomy? — Adopt Diátaxis for the
  categories AHEAD does not standardize; use its vocabulary as soft nudges in
  guide prose and authoring templates, not as spec annotations.
- Runbook naming: playbook vs runbook? — Runbook, industry-standard;
  "Google SRE calls the same artifact playbook" is documented in the guide.
- Style guide by name? — Yes, Google developer documentation style guide.

## Options

Considered:

- **Option A** — guide-only addition (no spec enforcement). Cheap; leaves
  reference-drift unenforceable.
- **Option B** — guide + `reference-updates` artifact in specs. Enforces
  updates through gates.
- **Option C** — Option B plus first-class `design-doc` artifact class.
- Rejected: annotate every workflow artifact with a Diátaxis mode. Too busy;
  Diátaxis stays a soft nudge.

## Decision

Selected **Option C** with runbook (not `operational-reference`) as the third
class name, and Diátaxis re-influence for the guide's tone and anti-pattern
language.

Three durable-reference classes:

1. `decision-record` — ADR shape (MADR).
2. `design-doc` — living design reference (arc42-shaped, C4-informed).
3. `runbook` — per-alert how-to (Google SRE Book–shaped).

Terminology chosen for LLM discoverability. Guide recommends Google developer
documentation style guide as the prose baseline.
